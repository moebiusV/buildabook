buildabook

buildabook turns a plain-text outline into a typeset book. One outline file drives the chapter numbering, the table of contents, and every cross-reference, so the book is a build artifact of a single source of order.

buildabook is a build tool for long manuscripts, written in Ada. It reads outline.txt, resolves {{token}} cross-references inside the chapter source files, and emits a Typst book.typ plus a number_map.csv audit. It is the shared build script of three book projects, extracted into one program.

Why it exists

A long manuscript has a property that a single prose pass does not: every number and every cross-reference is a claim about the whole book, and those claims go stale the moment the structure changes. An LLM is good at prose and bad at that bookkeeping. It writes "see Chapter 14" and, ten chapters later, inserts a chapter so that 14 becomes 15 without noticing the reference.

buildabook removes that failure mode by separating identity from rendering. The writer, human or LLM, never writes a number. It writes a stable reference, {{c:id00042}}, and the number is computed at build time from the row order of outline.txt. The UUID (id00042) is a name, not a number: its digits are not the chapter's number, and a chapter named c:id00042 can render as "Chapter 1" if it sits first in the outline. Inserting, deleting, or reordering a chapter is one line in the outline; every reference in the prose follows on the next build. A number is never baked into a title, so a renumber never rewrites prose.

The same mechanism covers the other places an LLM invents instead of computes:

  • Page numbers are never written by hand. {{page:id90001}} resolves through a native Typst lookup, so a reference stays correct across repagination.
  • The table of contents is generated from the outline, never typed.
  • A token's prefix is checked against the target's kind, so a wrong prefix or a typo'd UUID fails the build instead of shipping a wrong reference.
  • buildabook check fails on duplicate UUIDs, unmatched files, and unresolvable tokens before any PDF is produced.

The division of labour is deliberate. The LLM writes prose and stubs in the outline and chapter files; buildabook does the numbering, the references, and the consistency checks, which are the parts a prose pass cannot hold in its head.

What it does

  • Numbering from order. Chapters, parts, appendices, sections, and sub-entries are numbered from their row position in outline.txt, never from their UUID digits.
  • Directives. label, number, count, default, and none change the rendering regime for the entries of a prefix that follow them. The regime is snapshotted onto each entry, so a cross-reference renders with the regime in force at the target's position.
  • Cross-references. {{c:id00042}}, {{c:id00042|n}}, {{c:id00042|s}}, {{cc:id00001,00002}}, {{toc}}, and the s:/k: forms resolve at build time.
  • Page references. {{page:ID}}, {{c:id00042|page}}, and {{anchor:ID}} compile to native Typst locate() lookups, one pass, always exact.
  • Number map. number_map.csv lists every entry's UUID, kind, title, regime, computed number, and rendered designation, for auditing a regime change before compiling.
  • No giant tables. Markdown tables longer than a page are split with the header row repeated.
  • Cover spine. buildabook cover rewrites the spine width in cover.typ from the PDF page count, then compiles the cover.

The input language is specified in LANGUAGE.md.

Building

buildabook is Ada 2022, built with gprbuild. It does not need hbnf to build: the two parsers hbnf generates (the outline and book.conf, from grammars/*.hbnf) are checked in, and grammars/regen.sh regenerates them with hbnf 0.7.0 or later. The canonical toolchain is the ada-on-alpine overlay, packaged as the ada-toolchain:edge container image.

./configure
make
make check        # the aunit suite
make install      # installs buildabook and its man page

configure checks for gprbuild and the GNAT compiler (and that aunit is visible, for make check; hbnf is optional, for grammars/regen.sh). build.sh wraps the whole build in the container if you prefer that to a host toolchain.

Usage

buildabook               typst -> pdf -> cover, building what it can
buildabook typst         render rendered/book.typ + number_map.csv
buildabook pdf           compile rendered/book.typ with Typst
buildabook cover         update the cover spine, compile cover.typ
buildabook check         validate outline, filemap, and tokens; emit nothing
buildabook number-map    write number_map.csv only
buildabook uuid [c|p|a|d|n|u|s|k]  print the next free UUID
buildabook readme        rebuild README.md from DESCRIPTION.md + .desc sidecars

A command-line flag overrides book.conf, which overrides the built-in default. The default (buildabook with no subcommand) builds all three stages in order, and a missing or failing stage never blocks the next: no cover.typ just means the cover is skipped, never the book or the PDF.

How it works

The pipeline is one source, one document, one pass:

chapters/*.md + outline.txt + filemap.txt
      |
buildabook typst   parse the outline, number it, resolve every {{token}},
      |            split oversized tables, and emit rendered/book.typ
typst compile rendered/book.typ   ->   the PDF

The engine parses outline.txt with an hbnf-generated parser, applies the directives in one positional pass, and snapshots the regime onto each entry. It then builds a token map (c:id00042 -> "Chapter 42", and so on) and rewrites each chapter source, substituting tokens and planting page markers. The resulting Typst document imports a template and calls #chapter(...) once per entry.

Configuration

book.conf supplies per-book metadata and build paths, in obconf syntax (bareword or "quoted" directives, { } blocks, # comments):

title "Telegraph to Turbo Jet"
author "David Walther"
slug   speedrun-telegraph-to-turbo-jet
build {
    outline    outline.txt
    src        chapters
    out        rendered
    template   book.header.typ
    number-map number_map.csv
}
cover {
    source cover.typ
    output speedrun-cover.pdf
}

Every field is optional and every ---flag overrides it. The slug derives the PDF and cover output names; the build and cover blocks name the input and output paths. A malformed file is reported as file:line:col: message. It is parsed by hbnf's HBNF_Config crate, the same obconf grammar the outline uses.

The template

The engine ships a default Typst template (template/book.typ). A book may override it. The coupling contract an override must honour is documented in LANGUAGE.md: define book-title, running-title, fm-pages, body-pages, chapter(path, token, part, toc), pgan(id), pageof(id), and import cmarker.

Limitations

  • Line-oriented. A title or directive value runs to end of line, so it cannot contain a literal newline. There is no trailing-comment syntax.
  • Five-digit UUIDs. Each entry is addressed by a five-digit UUID (or idNNNNN.MINOR for a sub-entry). That is a finite namespace, and the writer must look up a UUID rather than a number when writing a reference. The number_map.csv is the look-up aid.
  • Sections need their token for page refs. A {{page:...}} reference to a section requires that section's heading to carry its token (## {{ s:id02104 }} — Title), because that token is what plants the page marker.
  • Sub-entries assume their parent. A k:idNNNNN.MINOR entry binds to the chapter with UUID idNNNNN; the engine does not verify that chapter exists at parse time.
  • Monolithic output. The book is one Typst document. Volume II or a split-book workflow is a Makefile-level concern, not an engine feature.
  • Toolchain weight. Ada, gprbuild, hbnf, and Typst are more to install than a Python script. In exchange the numbering and reference machinery is checked at compile time and the output is reproducible.
